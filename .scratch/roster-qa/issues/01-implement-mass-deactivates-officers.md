Found during `/roster` feature-parity QA (2026-09-08), testing `RosterBuilder`
against the local dev stack. Same code as the deployed GOV PaaS
`roster-dashboard` — applies there too, not a local-only issue.

## What happens

`POST /api/roster-patterns/:id/implement` (`artifacts/api-server/src/routes/rosterPatterns.ts:265-395`)
treats the officer roster embedded in the pattern being implemented as the
*complete new roster*: it matches each pattern officer to an existing officer
by name (case-insensitive, trimmed), upserts matches, and then **deactivates
every existing officer the pattern doesn't mention** (lines 328-330, 358-359,
393-395):

```js
// 2. Officers: upsert everyone in the new pattern (stable id — same name
// match keeps existing history attached), deactivate everyone else.
...
const keepIds = new Set(newOfficerRows.map((o) => o.id!));
const deactivateIds = existingOfficers.map((o) => o.id).filter((id) => !keepIds.has(id));
...
if (deactivateIds.length > 0) {
  await tx.update(officersTable).set({ active: false }).where(inArray(officersTable.id, deactivateIds));
}
```

Officers with an empty `name` field are skipped entirely before matching
(`if (!o.name?.trim()) continue;`, line 341) — so a pattern with unfilled
officer slots (e.g. a freshly-created, not-yet-populated pattern) deactivates
**every** existing officer on implement.

## Reproduction

1. Create a new roster pattern in `RosterBuilder` without filling in officer
   names for any slot (the natural first state of a new pattern).
2. Implement it.
3. Every existing officer becomes `active = false`. `/`, `/roster-builder`,
   and anywhere else that filters on `active` now shows empty/zero-strength
   ("No roster data found").

Confirmed via direct DB query before/after (`officers.active` count: 42 → 0)
and via `activity_log`, which only records a generic `roster-implement` event
with no detail on what changed.

## Why this matters more than a local test annoyance

- **No confirmation shown to the operator.** Implementing reads like "activate
  this rotation," not "replace the entire active officer roster" — there's no
  warning listing who's about to be deactivated before it happens.
- **Name-matching is fragile even when officers *are* filled in.** A typo,
  extra space, or different name casing in the pattern silently drops that
  officer into the deactivate bucket, even when preserving them was clearly
  the intent.
- **Real risk once GOV PaaS has real personnel data**, not just test fixtures.
  A manager iterating on a draft pattern (incomplete by definition, mid-edit)
  could mass-deactivate real officers with one click.

## Correct usage exists, just undiscoverable

`RosterBuilder.tsx` has a real officer search/autocomplete
(`OfficerCombobox`, fed by `/api/roster-plan/officer-names`) at each of the
two officer-name fields per unit — selecting from it guarantees an exact
match, so an implement done that way doesn't hit this. But nothing in the UI
requires using it, warns against leaving a slot blank, or explains the
implement-time consequence.

## Fix applied — fuller option (confirmation listing exactly who's affected)

New shared function `computeOfficerPlan(pattern)` in `rosterPatterns.ts`,
factored out of the implement route's own officer-matching logic so the
preview and the real action can never disagree. Backs a new endpoint:

`GET /api/roster-patterns/:id/implement-preview` — dry run, no writes,
returns `{ keepCount, deactivatedOfficers: [{id, name}] }`.

`RosterBuilder.tsx`'s Implement dialog now fetches this the moment it opens
(before the operator can type `IMPLEMENT`) and shows the real list of names
that would be deactivated, with extra emphasis if it's the entire active
roster. The real `implement` route was refactored to call the same
`computeOfficerPlan(pattern)` rather than duplicating the matching logic, so
the preview shown can't drift from what actually happens.

Name-matching itself (fuzzy, case-insensitive) was left as-is — not changed
to require exact combobox-selected ids. The visibility fix addresses the
core problem (silent, unwarned mass-deactivation); tightening matching
further is a separate, smaller follow-up if it ever proves necessary in
practice.
