Found during `/roster` QA (2026-09-08), testing `PHHoliday` for 9 Nov 2026 (an
OIL Monday). Same code as the deployed GOV PaaS `roster-dashboard` — applies
there too. Minor/UX severity, not data-affecting.

## What happened

```
POST /api/roster-plan/ph-extract-sunday/2026-11-09 404 (Not Found)
```
No visible error in the app itself — the PH ref roster for that date just
came up empty, with nothing telling the user why.

## Root cause — working as coded, not a crash

`rosterPlan.ts:1240-1281` (`POST /roster-plan/ph-extract-sunday/:date`)
correctly identified 9 Nov 2026 as a genuine OIL Monday (it already returns
400 if the date isn't a Monday, so reaching the 404 path confirms it passed
that check). Per the OIL rule, that means the preceding Sunday (8 Nov 2026)
should be a Public Holiday. The handler looked for an already-configured PH
roster for that Sunday, found none, and correctly returned:
`"No PH roster found for 2026-11-08. Configure Sunday's PH roster first."`

The real gap is on the frontend: `PHHoliday.tsx:344-358` calls this endpoint
inside a deliberately silent catch —

```js
try {
  const extractRes = await fetch(`/api/roster-plan/ph-extract-sunday/${date}`, { method: "POST", ... });
  ...
} catch { /* auto-extract failed silently */ }
```

— so a real manager hitting this in production would see an empty OIL
Monday roster with zero indication that Sunday needs to be configured first.

## Suggested fix direction (not decided/built)

Surface the 404's message (or a friendlier equivalent — "Configure the
preceding Sunday's PH roster first") via the page's existing message/toast
mechanism instead of swallowing it silently.
