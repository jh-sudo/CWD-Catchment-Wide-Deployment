> *This was generated by AI during triage.*

Found during `/roster` QA (2026-09-08), testing `PHHoliday` (`/public-holiday`)
— generating the 2027 PH roster produced a wall of React console warnings.
Same code as the deployed GOV PaaS `roster-dashboard` — applies there too.

## What happened

```
Encountered two children with the same key, `cp1a`. ...
```
...repeated for essentially every officer, unit by unit — `PHHoliday.tsx:786`
(`PHRosterTable`).

## Root cause

`GET /api/roster-plan/schedule?date=X` (`rosterPlan.ts:781-782`) is a
**weekly** endpoint — for every officer it maps over `weekDates` (all 7 days
of the week containing X), returning up to 7 duty rows per officer, not one:

```js
const duties = officersInRotation.flatMap((officer) => {
  return weekDates.map((dateStr, dayIdx) => { ... return { officerId: officer.id, date: dateStr, ... } })
});
```

`PHHoliday.tsx`'s `loadSchedule` (line 319-321) calls this expecting just the
one date it asked for, and only filtered by duty type — never by date:

```js
const working = (schedData.duties ?? [])
  .filter((d) => ["DAY", "PD", "ND"].includes(d.duty ?? d.targetDuty))   // no date check
  .map((d) => ({ officerId: d.officerId, ... }))
```

Since most officers work a DAY/PD/ND shift on more than one day per week,
each qualifying day became a separate row carrying the same `officerId` —
hence the duplicate-key warnings, uniformly across every officer.

Not just cosmetic: the "Scheduled" column was silently mixing in duty entries
from *other days that same week*, not just the PH date being viewed.

## Fix applied

Added `d.date === fetchDate` to the existing filter in `loadSchedule`
(`PHHoliday.tsx`), so only the actually-requested date's duties pass through.
