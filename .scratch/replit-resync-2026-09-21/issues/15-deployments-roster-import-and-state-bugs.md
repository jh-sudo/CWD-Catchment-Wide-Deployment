## What happened

1. **`parseRoster` duplicate-unit bug.** A roster import with two lines for the same unit code
   (common when a corrected line is pasted after an original) currently produces two duplicate
   team entries instead of keeping the last (corrected) one.
2. **Stale identity after roster changes.** When a unit's vehicle/partner changes between
   imports, old live deployment entries/assignments/vehicle positions under the old vehicleId
   become orphaned "ghost" records instead of migrating to the new identity. A crew device that
   pings its position after a roster re-import can also recreate a stale vehicle entry.
3. **ETag false-304 after restart.** `stateVersion` is a plain in-process counter starting at 0;
   after a restart/redeploy, a client's previously-cached ETag can coincidentally match the new
   counter value and get a false 304, showing stale deployment state.
4. **`/deployments/report` duplicate lines.** Can emit duplicate report lines per unit — one from
   a live entry, one from a pending assignment — for the same unit.

## Fix

1. Dedupe `parseRoster` by unit code, keeping the last line seen; report `duplicateUnits` in the
   response.
2. Add a `reconcileDeploymentStateWithRoster`-style pass that migrates old vehicleId-keyed
   records to the new identity when a roster re-import changes a unit's vehicle/partner, and
   have `/deployments/position` re-resolve the vehicleId from the current roster before saving.
3. Fix the ETag scheme to include a per-process epoch (e.g. process start time) alongside the
   counter, so a stale cached ETag from before a restart can never coincidentally match.
4. Dedupe `/deployments/report` lines per unit, preferring the roster-authoritative line when
   both an entry and a pending assignment exist for the same unit.
