## What happened

This repo already has a full "who's holding which plate today" backend —
`GET /api/vehicle-arrangement/officer-map` in `vehicleArrangement.ts` — built independently after
the fork. But several display surfaces don't call it and instead show a stale/wrong plate:

- `rosterPlan.ts`'s `buildSummary()` (feeds `GET /roster-plan/summary`, the FIRB deployment text)
  resolves vehicle as `hasAnchorCrew ? crew[0].officer.vehicle : ""` — the officer's static
  home-vehicle field, ignoring any reassignment.
- `TodaysRoster.tsx` and `RosterCycle.tsx` only set `vehicleMap[officerId] = d.vehicle` from the
  per-officer override row (usually blank).
- `RosterListView.tsx` falls back to `list[0]?.vehicle` (static ownership) when `vehicleMap` has
  no entry — explicitly reintroducing what Replit's own code comment calls out avoiding:
  *"Vehicle plate — one eligible officer per unit receives the daily server-resolved plate; never
  fall back to static ownership."*
- `CrewSchedule.tsx` and `MySchedule.tsx` show `selectedOfficer?.vehicle` / `myOfficer?.vehicle`
  (the officer's default vehicle), not the day's actual arrangement.
- `Layout.tsx`'s "Crew Today" top-bar widget has the same static-vehicle issue.

## Fix

Have all of the above call `GET /api/vehicle-arrangement/officer-map?date=` (which already
exists in this repo) instead of the officer's static `vehicle` field or a bare override value.
This is wiring existing infrastructure into more places, not building anything new.

## Comments

- 2026-09-21: Fixed on all listed surfaces.
  - `rosterPlan.ts`'s `buildSummary()`: factored the officer-map's resolution logic out of
    `vehicleArrangement.ts`'s route handler into an exported `resolveOfficerVehicleMap(date)`
    function (same file, so server-side callers can use it without an HTTP self-call), and had
    `buildSummary()` (converted to take a precomputed map, since it's a sync function) use it.
    This creates a two-way import between `rosterPlan.ts` and `vehicleArrangement.ts` (which
    already imported several functions the other way) — safe because every function on both
    sides is only ever called from inside request handlers, never at module top level, so the
    cycle never actually runs during module evaluation.
  - `TodaysRoster.tsx`, `RosterCycle.tsx`: now fetch the officer-map alongside schedule/leave data.
  - `RosterListView.tsx`: removed the `list[0]?.vehicle` static fallback entirely — shows nothing
    when the server map has no entry (correctly matching "OFF/REST/leave never get a vehicle"),
    rather than falling back to a possibly-wrong static record.
  - `CrewSchedule.tsx`, `MySchedule.tsx`: added a small per-selected-day fetch (cheaper than
    fetching the whole month's officer-maps, since only one day is shown in the detail panel).
  - `Layout.tsx`'s "Crew Today" widget: on inspection, no such widget exists in this repo's
    `Layout.tsx` — it only has a summary-text modal that calls the already-fixed
    `/api/roster-plan/summary` endpoint, so it benefits automatically with no separate change
    needed.
