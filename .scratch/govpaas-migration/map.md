## Destination

A migration spec/plan for taking this repo off Replit onto GitHub + GOV PaaS (Northflank-adjacent hosting): api-server, roster-dashboard, apa, and inspector hosted as services on GOV PaaS, with the current flat-JSON/Replit-Object-Storage "database" (`cloudPersistence.ts`) replaced by a proper relational Postgres schema. This map produces the plan — actual code changes and the real cutover happen in a later execution effort, driven by what this map decides.

Consolidated plan: [`spec.md`](spec.md) — all 17 decisions below are resolved; the plan is final. Actual code changes and the real cutover happen in a later execution effort.

- The current "database" is entirely flat JSON files in `artifacts/api-server/src/lib/cloudPersistence.ts`, mirrored to Replit's GCS-backed Object Storage. There is no real schema today — `@workspace/db` (Drizzle/Postgres) exists but is unused scaffolding.

- Plan, don't do (default wayfinder behavior — no override here).
- The GitHub repo itself doesn't exist yet — user will create it at deploy time, not during this planning effort. Tickets should treat "push to GitHub" as a future execution step, not something to do now.

## Decisions so far

- [Lock hosting scope](issues/00-scope-decisions.md) — Hosting: api-server, roster-dashboard, apa, inspector on GOV PaaS. Excluded: mockup-sandbox (static mockup, zero backend calls), deployment-tracker & wls-android-forwarder (mobile clients, not hosted). Destination is a plan, not the executed migration. Real relational schema (not lift-and-shove JSONB). Inspections (currently in-memory only) and VAPID push keys (currently regenerate on every restart) are in scope for the persistence fix. Existing data must be migrated, not discarded. Stale root binaries (`cwd-fleet-app-template.*`, other zips/docs) get dropped, not carried to GitHub.
- [GOV PaaS platform capabilities](issues/01-govpaas-platform-capabilities.md) — Researched as Northflank directly (not GOV.UK PaaS). Postgres via managed addon + secret-group env injection; both persistent volumes and a MinIO (S3-compatible) addon available for file storage; secrets via dashboard/CLI/Git templates; deploys are webhook-triggered container builds (Dockerfile or buildpacks), CI/CD native to the platform; one project can hold api-server/roster-dashboard/apa/inspector as separate services each with its own subdomain + auto TLS; logging captures stdout/stderr with optional sinks to Datadog/Loki/S3/HTTP. Full detail: [`docs/research/northflank-platform-capabilities.md`](../docs/research/northflank-platform-capabilities.md).
- [Hosting topology](issues/07-hosting-topology.md) — 4 separate Northflank services (api-server, roster-dashboard, apa, inspector), path-routed under one subdomain — mirrors the existing Replit topology (found in `artifacts/*/.replit-artifact/artifact.toml`) almost exactly via Northflank's native path-based routing. Same-origin throughout, no CORS work needed. Root `/` changes from redirecting to `/crew` (out of scope) to redirecting to `/roster/`.
- [Schema: roster & leave](issues/03-schema-roster-leave.md) — 11 tables (officers, roster_config, roster_maintenance_vehicles, roster_cycle_meta, roster_cycle_duties, roster_overrides, roster_swaps, leave_types, roster_leaves, leave_requests, roster_day_overrides + child table). Duty-resolution algorithm (override → Excel-cycle lookup → generator fallback) stays as application logic reading from Postgres, not materialized in the DB. Cycle grid keyed by unit_code not officer_id (crews share a duty). Found and flagged a likely existing bug: the "today's summary" path skips the Excel-cycle lookup step — fix bundled into the migration. Hardcoded `DEFAULT_OFFICERS` array gets deleted once the DB is seeded. Real staff PII is fine to migrate as-is since the repo/deployment will be private.
- [Schema: core ops state](issues/02-schema-core-ops-state.md) — 15 tables covering crms.json/wls.json/managers.json/config.json plus a newly-found gap: `deployments.ts`'s live flood-ops state (deployment entries, vehicle positions, swap requests, active alerts, reassignment history) was entirely in-memory, never persisted — included in scope, same reasoning as the inspections gap. Vehicle positions are latest-only (upserted, not a ping history). Login PINs become a DB settings row, not a secret. Alert history expanded to keep every broadcast (today only the current one survives), with an added `acknowledged_at` timestamp.
- [Schema: PH roster](issues/04-schema-ph-roster.md) — 6 tables. Two more persistence gaps found and included in scope: `ph-hr-ballot.json` (Hari Raya OIL draw pool — uploads but never restores) and `ph-rot-state.json` (fairness rotation cursor — never even uploads), both holding real already-progressing state. Confirmed `ALL_MUSLIM_OFFICERS` (religious-affiliation data, more sensitive than earlier PII) is still covered by the private-repo decision. Holiday calendar, rotation order, and exclusion rules stay as code constants, consistent with the roster & leave domain's treatment of duty templates. Redundant `UNIT_DEFAULTS` gets deleted.
- [Schema: inspections & push](issues/05-schema-inspections-push.md) — 5 tables (inspections, inspection_photos, inspection_lines, vapid_keys, push_subscriptions). Confirmed `push-subscriptions.json` is also a gap (push.ts never calls uploadToCloud at all), same class as vapid.json. Photos get a child table (individually addressed with pin numbers); line points stay as JSONB (no per-point identity). No open forks — straightforward application of patterns from the other schema tickets. Inspections have no durable source data to migrate (fresh start); this also unblocks the file storage for photos ticket.
- [Data backfill & cutover](issues/11-data-backfill-cutover.md) — Found that `artifacts/api-server/data/*.json` (all real data across every domain) is already committed to git, not just in Replit's GCS bucket — simplifies building/testing the migration script, but surfaces a secrets-hygiene problem (VAPID private key + password hashes in git history), flagged onto the repo-hygiene and secrets-migration tickets. Cutover: soft cutover with Replit staying live as fallback, final live data pull at actual cutover time (not trusting git copies alone), idempotent/repeatable migration script structured one-per-schema-domain, validation via row counts + spot checks + an explicit orphan-check for the fuzzy roster-cycle officer matching.
- [Repo hygiene checklist](issues/06-repo-hygiene-replit-surface.md) — Full drop/keep/port checklist for every Replit-specific artifact. Major find: `.agents/memory/` is Replit's own agent's persistent memory on this codebase — real domain knowledge (corrected a gap in the [roster & leave schema](03-schema-roster-leave.md): duty resolution is actually 4-tier, override > committed leave > cycle > generator, not the 3-tier originally documented), to be ported into this repo's own `CONTEXT.md`/`docs/adr/` convention rather than dropped. `attached_assets/` (100MB, actively used via `@assets` alias) needs pruning for unused files before committing, not a simple keep/drop.
- [Secrets & config migration](issues/08-secrets-config-migration.md) — One Northflank secret group scoped to api-server only. VAPID key carried forward as-is (avoids forcing re-subscription). `SESSION_SECRET`'s insecure fallback removed (fail-fast, matching the PORT/DATABASE_URL pattern). Session cookie `secure` flag becomes `NODE_ENV`-aware, safe since Northflank auto-provisions TLS. `cloudPersistence.ts` confirmed fully deletable.
- [File storage for photos](issues/09-file-storage-photos.md) — Northflank's managed MinIO addon (S3-compatible), chosen over a persistent volume (access mode fixed at creation, would constrain future scaling) and Postgres bytea. Upload via memoryStorage + PutObject (multer's validation unchanged). Serving stays proxied through api-server rather than presigned URLs, matching the current (unauthenticated, UUID-obscured) access model exactly rather than silently changing it. No backfill needed — inspections have no durable data today. Resolves the MinIO-credentials follow-up flagged in the secrets ticket.
- [Deploy/CI pipeline](issues/10-deploy-ci-pipeline.md) — Dockerfile per service (mirrors each artifact's existing Replit build command), GitHub Actions orchestrates builds + triggers Northflank deploys, and Postgres migrations (`drizzle-kit push`) run as a manually-triggered `workflow_dispatch` job rather than automatically on every deploy. Resolves the repo hygiene ticket's `post-merge.sh` follow-up — its `pnpm --filter db push` line becomes that manual job's payload.
- [Staging environment](issues/12-staging-environment.md) — **No dedicated staging/pre-production environment on GOV PaaS**, decided against both for the migration cutover and as a permanent ongoing environment. The migration cutover is already covered by ticket 11's soft-cutover validation window (production stood up and validated before DNS switches, Replit as fallback). For ongoing future development, rejected in favor of local dev (pnpm workspace against a local Postgres seeded from a prod dump) plus the existing manual migration gate (ticket 10) — a full second 4-service/Postgres/MinIO mirror was judged disproportionate cost/complexity for a small-scale internal tool. Escape hatch if ever needed: Northflank's git-branch build triggers support ad hoc PR-preview builds on demand, not a standing environment.
- [Domain/DNS/TLS](issues/13-domain-dns-tls.md) — Domain is `[project name].[team name].stg.paas.sandbox.gov.sg`, auto-provisioned per-project by the GOV PaaS sandbox platform — not self-registered, no DNS records for the team to manage. Confirmed via a doc check that Northflank's generic free default hostnames (`*.code.run`) do **not** support path-based routing (requires a verified custom domain first) — would have broken ticket 07's same-origin topology; the gov-provisioned domain sidesteps this since it's confirmed pre-verified and ready for path routing out of the box. TLS assumed auto-provisioned (Let's Encrypt, matching Northflank's general custom-domain behavior) but not independently confirmed for this gov instance — flagged as a post-deploy check, not a blocker. No separate "real" custom domain planned; goal is just to get it deployed. Doesn't reopen ticket 12 — a separate prod tier exists at the platform level, but moving to it isn't this migration's goal.
- [Logging/monitoring/alerting](issues/14-logging-monitoring-alerting.md) — **No log sink, no alerting** — stays on Northflank's native stdout/stderr capture (dashboard viewer), matching today's Replit setup (`logger.ts`: plain pino to stdout, nothing downstream) exactly. No code changes needed. Alerting (deploy failures, error-rate spikes) deferred entirely to a later effort — nothing like it exists today, would be genuinely new infrastructure. Same disproportionate-for-small-scale reasoning as ticket 12. Revisit only if the dashboard's (still-unconfirmed) log retention window proves too short for post-incident review, or an actual incident makes the alerting gap concrete. Clarified scope note: "flood-ops alert broadcast" (officer-facing) is a domain feature already covered in ticket 02, not part of this infra-alerting ticket.
- [Mobile client config](issues/15-mobile-client-config.md) — **All build-time, no api-server involvement.** API base URL is inherently client-side (circular dependency rules out an api-server config endpoint for it); Maps key stays client-side too rather than extending ticket 08's secret-group scope. Confirmed both mobile clients already work this way: deployment-tracker uses `EXPO_PUBLIC_API_URL` throughout with a Replit fallback; wls-android-forwarder's `DEFAULT_API_URL` is just a fallback constant — its Settings screen already lets a user edit/persist the API URL at runtime via `SharedPreferences`, no rebuild needed. Leaves only a future execution-time task: update the fallback/default values once ticket 13's real domain is live. Maps-key native-build wiring (app.json → app.config.js conversion) stays deferred, non-blocking, per the ticket's existing notes.
- [Git history credential scrub](issues/16-git-history-credential-scrub.md) — A loose end from ticket 06 that never got its own ticket number: `vapid.json`'s private VAPID key and `managers.json`'s bcrypt password hashes are committed to git history. **Resolved: scrub history** (`git filter-repo`/BFG) before the eventual GitHub push, rather than accepting it under the private-repo PII reasoning — credentials are a stricter risk category, sharpened by ticket 08's decision to carry the VAPID key forward unrotated (an unscrubbed leak would stay live indefinitely). Must happen before the GitHub repo is created, not retrofitted after collaborators/CI have cloned.
