## Question

Design the relational Postgres schema for the inspections & push-notification domain — the two persistence gaps found during scoping, neither of which is in `cloudPersistence.ts` today:

- Inspections: currently an in-memory `Map<string, Inspection>` in `artifacts/api-server/src/routes/inspections.ts`, with uploaded photos written to local disk (`uploads/inspections/`) via multer and never synced anywhere durable.
- VAPID push keys: currently autogenerated on first boot and written to a local file (`artifacts/api-server/src/routes/push.ts`, `data/vapid.json`) outside the cloud-persisted file list, so they regenerate on every restart. Also consider whether push *subscriptions* themselves (endpoints managers/officers have registered) are persisted anywhere — check `usePushSubscription.ts` on the frontend and the corresponding backend route.

Read the `Inspection` type, the routes, and the push subscription flow, then work through with the user: tables for inspections (+ line items, + photo references), where photo *binary data* actually lives (this feeds into the separate file/object storage ticket — don't decide the storage mechanism here, just the schema/reference shape), and how VAPID keys + subscriptions get stored so they survive restarts.

## Answer

### Findings

- **`push-subscriptions.json` is also a persistence gap**, same class as `vapid.json`: `push.ts` never calls `uploadToCloud` at all (confirmed by grep — no match in the file). Subscriptions are written to local disk (`saveSubs()`) but never cloud-synced, so they're lost on any container replacement, not just a restart.
- Photos are individually addressed today (`GET /inspections/:id/photos/:photoId/file`, each carrying a `pinNumber` used for map-pin labeling) — real entities with their own identity, not just an opaque blob array.
- Lines have identity (`lineId`) but no individual sub-routes reference a line by id — just a `points: {lat,lng}[]` polyline with no per-point identity.
- Push subscription dedup/removal already works by `endpoint` in the current code (`subs.filter(s => !dead.includes(...endpoint))`), so `endpoint` is the natural key already in use, not a synthetic id.

### Proposed tables

- **`inspections`** — replaces the in-memory `Map<string, Inspection>`: `id TEXT PRIMARY KEY`, `team_id TEXT`, `team_name TEXT`, `vehicle_number TEXT`, `officers TEXT` (free text, matches source — not normalized to officer records), `shift TEXT`, `started_at TIMESTAMPTZ`, `completed_at TIMESTAMPTZ`, `status TEXT CHECK (status IN ('active','completed'))`
- **`inspection_photos`** — child table (`InspectionPhoto`): `photo_id TEXT PRIMARY KEY`, `inspection_id TEXT NOT NULL REFERENCES inspections(id)`, `filename TEXT` (a reference into whichever storage the [file storage for photos](09-file-storage-photos.md) ticket picks — not decided here), `original_name TEXT`, `label TEXT`, `remarks TEXT`, `lat NUMERIC`, `lng NUMERIC`, `taken_at TIMESTAMPTZ`, `pin_number INT`
- **`inspection_lines`** — child table (`InspectionLine`): `line_id TEXT PRIMARY KEY`, `inspection_id TEXT NOT NULL REFERENCES inspections(id)`, `points JSONB NOT NULL` (ordered polyline, no per-point identity so no further normalization), `color TEXT`, `created_at TIMESTAMPTZ`
- **`vapid_keys`** — replaces `vapid.json` (the original gap), singleton row: `public_key TEXT NOT NULL`, `private_key TEXT NOT NULL`
- **`push_subscriptions`** — replaces `push-subscriptions.json` (the newly-found gap): `endpoint TEXT PRIMARY KEY` (natural key, matches existing dedup logic), `auth_key TEXT NOT NULL`, `p256dh_key TEXT NOT NULL`, `type TEXT CHECK (type IN ('manager','crew'))`, `vehicle_id TEXT`, `officer_id TEXT REFERENCES officers(id)`, `saved_at TIMESTAMPTZ`

No open forks in this domain — mostly a direct application of patterns already established in the other schema tickets (child tables for individually-addressed sub-entities, natural keys where the code already dedupes that way, JSONB for simple ordered leaf data with no independent identity).

This feeds into [data backfill & cutover](11-data-backfill-cutover.md): inspections have no durable source to migrate from today (in-memory only), so this is a fresh start rather than a backfill; `push-subscriptions.json` and `vapid.json` do have live local data worth carrying over if accessible before cutover. This also unblocks [file storage for photos](09-file-storage-photos.md), which was waiting on this ticket's schema/reference shape.
