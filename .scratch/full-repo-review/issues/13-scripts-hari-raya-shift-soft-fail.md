## Agent Brief

**Category:** bug (data-safety, soft-fail rather than silent)
**Summary:** The PH-roster generator can assign an officer to a shift the racial/religious rules say they can't work on Hari Raya, with only an easy-to-miss inline remark as a warning.

**Current behavior:**
`scripts/generate-ph-roster.mjs:136-144` — on Hari Raya dates, officers in
`RACIAL_RULES.HARI_RAYA_DAY_ONLY` must land on a DAY shift, but only the first
3 auto-selected slots get `"DAY"`; if more than 3 of the 6 selected units
happen to be HR-day-only-restricted, the overflow still gets assigned `"PD"`.
The code does self-flag this with a per-row `remarks: "⚠ Must be DAY on Hari
Raya — verify shift"` (~lines 157-158), so it's not silent, but nothing blocks
the write — if the remark is missed during manual review before
`ph-roster-ref.json` is committed (which later feeds directly into the
`04-ph-roster.ts` backfill), a restricted officer could ship into production
with the wrong shift on a religious holiday.

**Desired behavior:**
This condition either hard-fails generation (forcing a human to resolve the
slot assignment before a file is written) or is surfaced more forcefully than
an inline row remark — e.g. a non-zero exit code and a separate summary
section listing every violation, so it can't be missed in a quick review.

**Key interfaces:**
- `scripts/generate-ph-roster.mjs` — slot-assignment loop around line 136-144

**Acceptance criteria:**
- [ ] Running the generator against an input where more than 3 selected units are `HARI_RAYA_DAY_ONLY`-restricted on the same Hari Raya date either fails the run or prints a clearly separated warning summary (not just an inline `remarks` cell) and exits non-zero
- [ ] The existing correct case (≤3 restricted officers) is unaffected

**Out of scope:**
- Adding a `--dry-run` flag to this script (noted separately as a smaller, lower-priority inconsistency with the rest of `scripts/`, where every DB-touching script supports one — this script only writes a git-tracked JSON file, so the risk is lower)

**Fixed.** `autoAllocate()` now takes a shared `violations` array; whenever
`forced.length > 3` for a Hari Raya slot (more restricted units selected than
can fit in the 3 DAY slots) it records `{date, phName, restrictedUnits,
overflowCount}` instead of only relying on the inline `remarks` cell. After
both years are generated, if `violations` is non-empty the script prints a
clearly separated, itemized summary to stderr and calls `process.exit(1)`
**before** `fs.writeFileSync` — `ph-roster-ref.json` is never touched on a
violating run, satisfying the "forcing a human to resolve... before a file is
written" option from Desired Behavior. The inline per-row `remarks` warning
is left in place as a secondary signal (now effectively unreachable in
practice since a violating run never gets to the write step, but harmless to
keep).

Verified two ways:
- **Isolated logic test** (synthetic 6-unit rotation, 4 fake
  `HARI_RAYA_DAY_ONLY` names, run in scratch — not the real data) confirmed a
  4-restricted-unit selection produces exactly 1 violation with
  `overflowCount: 1`, and a 3-restricted-unit selection produces 0 violations
  with the existing DAY/PD assignment unchanged. Test file deleted after.
- **Real run** of the patched script against the actual `roster-officers.json`
  / `ph-roster-ref.json` (current real rotation has ≤3 restricted units on
  every Hari Raya slot, so no violation): completed normally, exit 0, wrote
  successfully.

**Found something else while doing that real run, not part of this ticket —
