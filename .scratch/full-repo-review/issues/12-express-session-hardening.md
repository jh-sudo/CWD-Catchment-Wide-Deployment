## Agent Brief

**Category:** bug (security hardening, plausible severity)
**Summary:** No session-ID regeneration across the login/MFA trust boundary, and sessions are backed by the non-production-safe in-memory store.

**Current behavior:**
1. **No `regenerate()` on privilege escalation** — nowhere in
   `artifacts/api-server/src/routes/auth.ts` is `req.session.regenerate()`
   called. `/manager/auth/login` (~lines 240-253), `/manager/auth/mfa/challenge`
   (~286), and `/manager/auth/mfa/verify-setup` (~557) all promote a session
   from unauthenticated/pending to authenticated by mutating fields
   (`pendingMfaManagerId` → `managerId`) on the *same* session ID, rather than
   regenerating it first. (`logout` does correctly call
   `req.session.destroy`.) A session ID established before login stays valid
   and becomes privileged after login completes — the standard session-fixation
   pattern. Real-world exploitability requires an attacker to plant a session
   cookie in the victim's browser first (narrowed, but not eliminated, by
   `httpOnly`+`secure` cookies already being set correctly).
2. **Default in-memory session store in production** — `app.ts:43-54`
   configures `session(...)` with no `store` option, and no session-store
   package (`connect-redis`, `connect-pg-simple`, etc.) is in `package.json`.
   Node's default `MemoryStore` is explicitly documented as not
   production-safe: no pruning of expired sessions, and it's per-process, so
   it doesn't survive restarts and doesn't share state across replicas. Given
   the app is mid-migration to a PaaS (Northflank) and already treats
   `SESSION_SECRET`/`MFA_ENCRYPTION_KEY` as required prod config, this looks
   like an oversight. Impact: every deploy/restart force-logs-out all
   managers/crew, and horizontal scaling beyond one replica would cause random
   session loss.

**Desired behavior:**
1. `req.session.regenerate()` is called (preserving needed pending state)
   right after password verification and again right after MFA success.
2. Sessions are backed by a persistent store (`connect-pg-simple`, reusing the
   existing `DATABASE_URL`, is the lowest-lift option given Postgres is
   already the primary datastore).

**Key interfaces:**
- `artifacts/api-server/src/routes/auth.ts` — login/challenge/verify-setup handlers
- `artifacts/api-server/src/app.ts:43-54` — session middleware config

**Acceptance criteria:**
- [ ] Session ID changes at each trust-boundary crossing (pre-auth → pending-MFA → authenticated)
- [ ] Sessions survive an api-server restart and are shared correctly across multiple replicas (verify with `connect-pg-simple` or equivalent)

**Out of scope:**
- Cookie flags themselves (`httpOnly`/`secure`/`trust proxy`) — already correctly configured, not a regression here

## Comments

> *This was generated by AI during triage.*

**Fixed, both items.**

1. **`regenerate()` at every trust-boundary crossing.** Added a
   `regenerateSession()` helper (promisified — `express-session`'s
   `regenerate()` is callback-only) and called it in all four places a session
   is promoted to a more-privileged state: `/manager/auth/login` (before
   setting either `pendingMfaManagerId` or `managerId`), `/manager/auth/mfa/
   challenge` and `/manager/auth/mfa/verify-setup` (pending → authenticated),
   and `/api/crew/auth/login` (same pre-auth → authenticated pattern as the
   manager login, not explicitly named in the original brief but the same
   class of issue). `regenerate()` replaces `req.session` with a fresh
   object, so the old `delete req.session.pendingMfaManagerId` lines in the
   challenge/verify-setup handlers became unnecessary — the fresh session
   never has it.

2. **`connect-pg-simple` session store**, reusing the existing `pool` export
   from `@workspace/db` (no second connection pool). **Found and fixed a real
   bug while verifying live**: `connect-pg-simple`'s `createTableIfMissing`
   reads a `table.sql` file relative to its own package directory at
   *runtime* — that file isn't carried along when esbuild bundles this app
   into a single `dist/index.mjs`, so the option threw `ENOENT` in the built
   artifact (worked fine running from source, which is why `pnpm typecheck`/
   a naive review wouldn't have caught it). Fixed by creating the table
   ourselves with the same DDL connect-pg-simple ships (`CREATE TABLE IF NOT
   EXISTS`, no external file dependency), run once via `pool.query()` before
   the store is constructed — `app.ts` now uses a top-level `await` for this
   (safe here: `module: esnext`/`target: es2022`, esbuild bundles as ESM).

**Verified live** against local Postgres (not just `tsc`/build): built
`dist/index.mjs` and ran it directly (the same artifact that ships), then
walked a real account through both MFA paths with real TOTP codes
(`otplib.generate`) —
- registered a fresh manager account, logged in (enroll branch) → session id
  `S1`; completed `mfa/verify-setup` → id changed to `S2`.
- logged out, logged back in (now-enrolled account, challenge branch) → id
  `S3` (≠ `S2`); completed `mfa/challenge` → id changed to `S4`.
- `SELECT * FROM session` in Postgres showed the row for `S4`, confirming
  persistence (not just cookie-swapping).
- **Killed and restarted the server process**, then replayed the `S4` cookie
  against `/manager/auth/me` — still authenticated, confirming the session
  survived the restart (the actual acceptance criterion for item 2, not just
  "a store other than MemoryStore is configured").

Test account and session rows deleted from the local DB afterward; local
Postgres/MinIO containers stopped again. `connect-pg-simple` + `@types/
connect-pg-simple` added to `artifacts/api-server/package.json`.
