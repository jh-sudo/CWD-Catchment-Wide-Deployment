## Agent Brief

**Category:** bug (race condition — stale data can overwrite fresh data)
**Summary:** Navigating between dates quickly can leave the roster grid showing an older date's data under the correct date header.

**Current behavior:**
`artifacts/roster-dashboard/src/pages/TodaysRoster.tsx:123-165` (`load()`) and
`artifacts/roster-dashboard/src/pages/RosterCycle.tsx:60-105` (`loadDate()`)
each fire two `fetch()`s per date change and unconditionally call
`setDutyMap`/`setLeaveMap`/etc. with whatever comes back — there's no
request-id or `AbortController` check against the currently-selected date.
Paging quickly through dates (next/prev buttons, the touch-swipe gesture in
`TodaysRoster.tsx`, or the date picker) can let an older in-flight response
resolve after a newer one, silently overwriting the grid with the wrong
date's duty/leave data while the header still shows the correct (different)
date.

**Desired behavior:**
A stale response for a date the user has since navigated away from is
ignored, not applied to state.

**Key interfaces:**
- `artifacts/roster-dashboard/src/pages/TodaysRoster.tsx` — `load()`
- `artifacts/roster-dashboard/src/pages/RosterCycle.tsx` — `loadDate()`

**Acceptance criteria:**
- [ ] Rapidly navigating dates (e.g. holding next/prev, or fast swiping) never leaves the grid showing a date other than the one currently selected
- [ ] Implemented via `AbortController` (aborting the previous request on navigation) or a captured request-date check before each `setState` call

**Out of scope:**
- Any other data-fetching flow in the app not exhibiting this pattern (spot-checked, not found elsewhere in this slice)

**Fixed.** Added a per-component `activeLoadDateRef` (holds the date the most
recent `load()`/`loadDate()` call was made for) in both
`TodaysRoster.tsx` and `RosterCycle.tsx`. Each fetch now checks the ref against
its own captured date immediately before every `setState` call (schedule data
and leave data are checked separately, since they resolve independently) and
bails out if the user has since navigated elsewhere. The `finally` block's
`setFetching`/`setLoading` toggle is guarded the same way, so a superseded
request can't flip the spinner off while a newer one is still in flight.
Chose the "captured request-date check" option over `AbortController` since
the existing code already threads `dateStr`/`ds` through the whole function —
no new signal plumbing needed. Verified no new `tsc --noEmit` errors (diffed
against a stash of the same command — output is byte-identical, all
pre-existing and unrelated to these two files).
