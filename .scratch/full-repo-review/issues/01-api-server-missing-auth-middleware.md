## Agent Brief

**Category:** bug (security — broken access control)
**Summary:** Multiple route files in the API server accept mutating/destructive requests from unauthenticated callers.

**Current behavior:**
No auth check anywhere in the file:
- `src/routes/inspections.ts` — entire file, including `DELETE /api/inspections` (defaults to `mode=all`, deletes every inspection row + MinIO photo objects)
- `src/routes/wls.ts` — entire file, including `POST /wls/ingest` / `/wls/ingest-batch` (can inject fake CRITICAL water-level readings, which trigger real push alerts to managers) and `DELETE /wls/:stationId` / `DELETE /wls?all=1` (erases real flood-monitoring data)

`requireManager` missing on specific routes, while present elsewhere in the same file:
- `src/routes/deployments.ts` — `roster/import`, `roster` DELETE, `alert/broadcast`, `alert` DELETE, `deployments/reset`, `deployments/deduplicate`, `deployments/assign`, `deployments/pre-assign`, `deployments/clear-assignments`, `deployments/assignments/respond`, `deployments/locations` POST/PUT/DELETE, `deployments/rain-auto-assign`, `deployments/auto-assign`. Also `GET /deployments/state` leaks live officer names + GPS coordinates to anyone.
- `src/routes/rosterPlan.ts` — `PUT /roster-plan/config`, `POST/PUT/DELETE /roster-plan/officers[/:id]`, `POST/DELETE /roster-plan/leave[/:id]`, `PUT/DELETE /roster-plan/swaps/:id`. (The officer POST/PUT also spreads `...req.body` straight into the DB write with no field allowlist — tracked separately in `06-request-validation-not-enforced.md`.)
- `src/routes/crms.ts:687,716` — `POST /crms/:id/resolve` and `.../comment` have no session check at all, not even `requireCrew` (a comment in the source says "no manager auth" intentionally, but this goes further — there's no crew check either, so attribution fields like `vehicleId`/`unitCode` can be spoofed by anyone).

Concrete failure: `curl -X POST https://.../api/deployments/reset` from anywhere on the internet wipes the live incident/deployment board during an actual flood response, with no credentials.

**Desired behavior:**
Every mutating/destructive route in these files requires the same session-based `requireManager`/`requireCrew` check already used correctly elsewhere in the same files, so an anonymous request gets a 401/403, not a successful write.

**Key interfaces:**
- `requireManager` / `requireCrew` / `requireAdmin` middleware — `artifacts/api-server/src/routes/auth.ts:164-223`

**Acceptance criteria:**
- [ ] `inspections.ts`: every mutating route requires `requireManager` (or the appropriate role)
- [ ] `wls.ts`: ingest routes require a shared secret or `requireManager`; delete routes require `requireManager`
- [ ] `deployments.ts`: every route listed above requires `requireManager` (crew-self-service actions keep `requireCrew`)
- [ ] `rosterPlan.ts`: every route listed above requires `requireManager`
- [ ] `crms.ts`: `resolve`/`comment` require at least `requireCrew` (confirm with a human whether that's the intended trust level, or if it should be `requireManager`)
- [ ] A request to any of the above routes without a valid session now returns 401/403 instead of succeeding

**Out of scope:**
- Adding request-body validation (tracked separately in `06-request-validation-not-enforced.md`)
- Adding a scoped single-inspection delete route (tracked separately in `04-inspections-missing-scoped-delete-route.md`)
- Rate-limiting the `X-Manager-Pin` bypass inside `requireManager` itself (tracked separately in `03-manager-pin-bypass-no-rate-limit.md`)

Adding `requireManager`/`requireCrew` to routes with a `:param` in the path
surfaced a pre-existing TS+Express inference quirk (multiple handlers on a
route defeats the path-literal `req.params` typing, widening it to
`string | string[]`) — fixed the same way the codebase already does
elsewhere (`rosterPlan.ts`'s `ph-extract-sunday`/`ph-apply` routes): destructure
`req.params` with an explicit `as { id: string }` cast at the top of each
affected handler (`rosterPlan.ts` officers/leave/swaps routes, `wls.ts`'s
`DELETE /wls/:stationId`, `crms.ts`'s resolve/comment routes).

Verified: `pnpm --filter api-server typecheck` and `build` both clean. Ran
the real server locally (local Postgres/MinIO via Docker, `pnpm --filter
