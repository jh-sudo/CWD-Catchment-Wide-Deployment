## Agent Brief

**Category:** bug (correctness — generated types don't match reality)
**Summary:** Three concrete places where `openapi.yaml`/generated Zod schemas disagree with either the DB schema or what the server actually sends.

**Current behavior:**
1. `RosterOfficerInput` (`openapi.yaml:774-791`, `CreateRosterOfficerBody` in
   `lib/api-zod/src/generated/api.ts:324-337`) is shared between create and
   update, so `name`/`unitCode`/`vehicle`/`catchment`/`teamSlot`/`crewPosition`
   are all optional even on create — but `lib/db/src/schema/officers.ts:12-17`
   marks `name`/`unitCode`/`teamSlot`/`crewPosition` `.notNull()`. A `POST
   /roster-plan/officers` with a legal-per-schema partial body will hit a
   Postgres NOT NULL violation instead of a clean validation error. The same
   shared schema also lets `active` be set on create, despite its own
   doc-comment saying it's "not settable on create."
2. `teamCount` (`lib/api-zod/src/generated/api.ts:257-298`,
   `RosterConfigTeamCount`/`RosterConfigInputTeamCount` in
   `api.schemas.ts:145-176`) declares `16 | 20 | 24 | 28` as legal, but
   `lib/db/src/schema/rosterConfig.ts:16` has a CHECK constraint allowing only
   `(20, 24, 28)`, and `rosterPlan.ts:504` independently validates the same
   three values server-side. The frontend already had to route around the
   wrong generated type with unsafe casts:
   `artifacts/roster-dashboard/src/components/Layout.tsx:245` and
   `Roster.tsx:275` do `parseInt(val, 10) as 20 | 24 | 28`.
3. `RosterSwap`/`GetRosterSwapsResponseItem` (`lib/api-zod/src/generated/api.ts:454-469`,
   `api.schemas.ts:221-238`) is missing `type` and `phName`, which
   `lib/db/src/schema/rosterSwaps.ts:36-37` has and which
   `rosterPlan.ts:780` actually returns (`res.json(swaps)` on the raw Drizzle
   row type). The one real consumer,
   `artifacts/roster-dashboard/src/pages/ApplicationsManage.tsx:105-113`,
   needs `swap.phName`/`swap.type` and can only get them by typing the whole
   `SwapCard` prop as `swap: any` (line 110), losing type safety for the rest
   of that component too.

Minor/lower-confidence, same category: `VehiclePosition`/`UpdatePositionRequest`
also omit `partner`/`shift`, which `deploymentVehiclePositionsTable` has and
`GET /deployments/state` actually serializes — no known active consumer of
those two fields yet, but worth fixing alongside the above while in this
file.

4. `AssignmentRespondRequest`/`RespondToAssignmentBody`
   (`openapi.yaml:562-584`, `api.ts:164-174`) makes `vehicleNumber`,
   `unitCode`, `partner`, `shift`, `eta`, `etaMinutes` all optional
   regardless of whether `accepted` is `true` or `false`, even though
   ETA/unit info presumably only matters when accepting. Not currently
   enforced anywhere (validation is unwired per
   `06-request-validation-not-enforced.md`), so low urgency, but worth a
   `.refine()`/discriminated union once that ticket wires validation in.

**Desired behavior:**
The OpenAPI spec (and its generated Zod/TS output) matches both the DB schema
and what the server actually sends/accepts.

**Key interfaces:**

Fixed items 1-3 and the minor VehiclePosition item by editing
`openapi.yaml` and regenerating (`pnpm --filter @workspace/api-spec run
codegen`):

1. Split `RosterOfficerInput` into `RosterOfficerCreateInput` (requires
   `name`/`unitCode`/`teamSlot`/`crewPosition` — matches
   `officers.ts`'s `.notNull()` columns with no default; `vehicle`/
   `catchment` stay optional since those columns have a `""` default) and
   `RosterOfficerUpdateInput` (all optional, including `active`, which is
   no longer present on the create schema at all). `createRosterOfficer`/
   `updateRosterOfficer` now reference the matching schema.
2. `teamCount` enum tightened from `[16, 20, 24, 28]` to `[20, 24, 28]` on
   both `RosterConfig` and `RosterConfigInput`.
3. `RosterSwap` gained `type`/`phName` (nullable strings, matching the DB
   columns). Updated `ApplicationsManage.tsx`'s `SwapCard` to type its
   `swap`/`onReview`/`onDelete` props as `RosterSwap` instead of `any` —
   also dropped a dead `swap.kind === "PH"` check in the same expression
   (`kind` was never a real field anywhere in the schema or DB).
4. `VehiclePosition`/`UpdatePositionRequest` gained optional `partner`/
   `shift`, matching `deploymentVehiclePositionsTable` and what
   `POST /deployments/position` already accepts.

**Item 4 (`AssignmentRespondRequest`'s conditional-required fields)
deliberately deferred** — the ticket's own text already recommends this
("worth a `.refine()`/discriminated union once that ticket wires
validation in"). Since nothing in this codebase enforces schemas at
runtime yet (`06-request-validation-not-enforced.md`), and OpenAPI/JSON
Schema has no established `oneOf`/discriminator precedent anywhere else in
this spec, adding the conditional requirement now would mean hand-layering
a `.refine()` on top of the generated schema in a way that survives the
next `codegen` run — better done as part of `06`'s actual wiring work,
where it'll live right next to the `assignments/respond` route handler
that needs it.

**Found and fixed an unrelated cross-platform bug in the codegen pipeline
itself** while verifying: `codegen`'s `echo '...' > index.ts` step relied
on POSIX shell quote-stripping. pnpm runs package.json scripts through
`cmd.exe` on Windows, which does *not* strip single quotes — the file
ended up containing the literal quote characters, turning
`export * from "./generated/api";` into a no-op string-literal statement
that silently exported nothing. `lib/api-zod/dist/index.d.ts` came out
empty, breaking every consumer's type resolution with no visible error
(`tsc --build` doesn't error on a syntactically-valid-but-meaningless
string literal). Replaced the `echo` step with
`lib/api-spec/write-zod-index.mjs`, a small Node script that writes the
file directly — no shell quoting involved.

Verified: `pnpm --filter @workspace/api-spec run codegen` runs clean and
`lib/api-zod/dist/index.d.ts` now actually contains the export.
`pnpm --filter api-server typecheck`/`build`,
`pnpm --filter roster-dashboard typecheck`/`build`, `pnpm --filter apa
typecheck`, and `pnpm --filter inspector typecheck` all clean (roster-dashboard's
remaining typecheck errors are the same pre-existing/unrelated ones
confirmed present on `main` before any of this work).
