## Agent Brief

**Category:** bug (security — access control implemented in the wrong layer)
**Summary:** apa's "Admin access required" login screen only gates the UI; the flood-risk-area and deployment data it's meant to protect ships in the public static JS bundle regardless of auth.

**Current behavior:**
`artifacts/apa/src/App.tsx` imports `src/data/presetLocations.ts` and
`src/data/catchments.ts` directly (`PRESET_LOCATIONS`, `FRA_CLUSTERS`,
`FLOOD_DOTS` — 25 deployment points, 4 flood-risk-area clusters, ~90 flood dot
coordinates). Since apa is deployed as a static SPA (`serve = "static"` per
`.replit-artifact/artifact.toml`), Vite bakes this data into the shipped JS
chunk with no server-side check at all. The login screen and `AuthState`
gating in `App()` only control whether the map UI *renders* — anyone can read
the underlying data straight out of the downloaded bundle (devtools / view
source / unzip the build output) without ever authenticating.

**Desired behavior:**
If this operational data is meant to be admin-only (as the login screen
implies), it's served from an authenticated API endpoint at runtime instead
of being bundled at build time.

**Key interfaces:**
- `artifacts/apa/src/data/presetLocations.ts`, `src/data/catchments.ts` — move behind an authenticated endpoint
- `artifacts/apa/src/App.tsx` — fetch instead of static import, gated on the (now-working, once `02-mfa-rollout-incomplete-frontends.md` is fixed) authenticated session

**Acceptance criteria:**
- [ ] Flood-risk-area/deployment coordinate data is not present in the built JS bundle for an unauthenticated request
- [ ] The map still renders the same data for an authenticated admin session

**Out of scope:**
- Related low-severity note found in the same pass: `index.html` and
  `public/robots.txt` opt this internal tool into search-engine indexing
  (`<meta name="robots" content="index, follow">`, `Allow: /`) — likely
  inherited template boilerplate, worth turning off but not a security hole
  on its own.
