## Agent Brief

**Category:** bug (data loss / false success feedback in a field-crew app)
**Summary:** Three flows in the inspector app silently fail or lie about success when a request to the backend fails, instead of surfacing an error like the app's own photo-upload flow already does.

**Current behavior:**
- `artifacts/inspector/src/App.tsx:105-127,763-784` (`TeamSelect.handleStart` /
  `handleTeamStart`) — `onStart(team)` isn't awaited, `setLoading(true)` runs
  regardless, and there's no `try/catch`. If `POST /api/inspections` fails or
  the fetch throws (plausible for field crews with poor connectivity), nothing
  ever calls `setLoading(false)` — the "Starting…" button is stuck forever;

- `artifacts/inspector/src/App.tsx:407-419` (`handleSubmit`) — the `PUT

  deleted server-side (e.g. via the bulk-clear button, see
  `04-inspections-missing-scoped-delete-route.md`), the backend 404s but the
  UI still shows "✅ Inspection Submitted" — the field crew walks away
  believing their report was recorded when it was silently dropped.
- `artifacts/inspector/src/App.tsx:382-397` (`finishLine`) — `setDrawPoints([])`
  runs unconditionally after the `fetch`, win or lose. A failed POST (or a
  thrown fetch, unhandled — no `try/catch`) discards the line the user just
  drew with no error message and no way to recover it.

**Desired behavior:**
All three flows check `res.ok` before treating a request as successful, wrap
the fetch in `try/catch`, and surface a retry-capable error state — matching
the pattern `handlePhotoSave` already uses in the same file.

Fixed all three flows, modeled on `handlePhotoSave`'s existing pattern
(try/catch, `res.ok` check, parse `body.error` for a message, `finally` to
reset the busy flag):

- `TeamSelect.handleStart` is now `async`, awaits `onStart(team)` in a
  try/catch, and always resets `loading` in `finally` — the button can no
  longer get stuck on "Starting…" forever. Added a `startError` state
  shown above the button; on error the button relabels to "Retry".
  `App.handleTeamStart` now throws (with the server's `error` message, or
  a status-code fallback) instead of silently `return`ing on `!res.ok`, so
  the error actually reaches `TeamSelect`'s catch block. `onStart`'s prop
  type updated to `Promise<void>` to match.
- `handleSubmit` now checks `res.ok` before calling `setDone(true)` and
  wraps the fetch in try/catch. A failed/404'd submit shows a `submitError`
  banner and relabels the button to "Retry Submit" instead of lying with
  "Inspection Submitted" — the in-progress report state is untouched.
- `finishLine` wraps the fetch in try/catch and only clears `drawPoints`
  on success. A failed save (or thrown fetch) keeps the drawn points on
  screen, shows a `lineError` banner, and the "Finish Line" button
  relabels to "Retry" (disabled while `lineSaving`).

All three error banners reuse the existing `.upload-error` CSS class for
visual consistency with `handlePhotoSave`'s error display.
