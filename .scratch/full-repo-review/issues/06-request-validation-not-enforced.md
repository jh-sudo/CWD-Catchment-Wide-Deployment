## Agent Brief

**Category:** bug (correctness — the validation layer is not actually wired in)
**Summary:** `lib/api-zod` defines ~30 request/response schemas, but only the health-check route validates against them — every other route trusts `req.body` unchecked.

**Current behavior:**
A repo-wide grep shows only `artifacts/api-server/src/routes/health.ts` calls
`.parse()` on any generated Zod schema. Every other route file that reads
`req.body` (`auth.ts`, `deployments.ts`, `rosterPlan.ts`, `crms.ts`,
`inspections.ts`, `leaveRequests.ts`, `phRoster.ts`, `push.ts`, `wls.ts`) does
a raw `req.body as {...}` cast. Example: `rosterPlan.ts:524-528` does
`db.insert(officersTable).values({ id: randomUUID(), ...req.body }).returning()`
— malformed, missing, or extra fields go straight to Drizzle/Postgres.
Failures surface as raw DB constraint violations (opaque 500s) instead of
clean 400s, and nothing stops type confusion (e.g. sending `teamSlot` as a
string, or including fields like `active` that the API doc says shouldn't be
settable on create).

**Desired behavior:**
Mutating routes validate `req.body` against the matching `lib/api-zod` schema
before touching the database, returning a 400 with a clear message on
failure.

**Key interfaces:**
- `lib/api-zod/src/generated/api.ts` — the existing (currently unused) schemas
- `artifacts/api-server/src/routes/health.ts` — the one existing correct example to follow
- `artifacts/api-server/src/routes/rosterPlan.ts:524-528` — good first target, since it's also the field-allowlist gap noted in ticket 01

**Acceptance criteria:**
- [ ] Every mutating route in the list above calls `schema.parse(req.body)` (or equivalent middleware) before using the body
- [ ] A request with a missing required field or wrong type gets a 400 with a useful message, not a raw DB error
- [ ] `rosterPlan.ts`'s officer create no longer accepts arbitrary extra fields (e.g. `active`) via `...req.body` spreading

**Out of scope:**
- Fixing the schema/DB drift itself (tracked in `10-api-contract-schema-drift.md`) — do that first or alongside, since validating against a schema that's already wrong (e.g. `teamCount: 16` being legal) won't help
