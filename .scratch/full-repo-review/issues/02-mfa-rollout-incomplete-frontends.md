## Agent Brief

**Category:** bug (broken authentication — full app lockout)
**Summary:** `artifacts/apa` and `artifacts/roster-dashboard` cannot log in any admin/manager/ic account — the mandatory-MFA response is silently mishandled as a role mismatch.

**Current behavior:**
- `artifacts/apa/src/App.tsx` (`LoginScreen.handleSubmit`, ~lines 77-101): only branches on `data.role`. Since MFA-eligible logins never include `role` in this response, every correct-credential login falls into the `data.role !== "admin"` branch and shows "Admin access only. Your role: undefined". The session's `managerId` is never set (the server correctly did not authenticate the session yet, pending MFA), so there's no way to get past this screen at all — not even with correct MFA credentials, because the app never prompts for a code.
- `artifacts/roster-dashboard/src/context/AuthContext.tsx` (`login()`, ~lines 52-70) and `src/pages/Login.tsx`: same failure shape — `login()` only checks `!res.ok` (which is `false`, since the server returns HTTP 200 with the MFA-step payload), sets a bogus user with `role: undefined`, then `refresh()` hits `/manager/auth/me`, gets 401 (no session was ever authenticated), and resets `user` to `null`. The UI silently bounces back to the login screen with no error and no TOTP field. A repo-wide grep for `mfa`/`totp`/`challenge` in `roster-dashboard/src` returns zero hits outside an unrelated shadcn `input-otp.tsx` primitive that isn't wired to anything.

Crew accounts are unaffected in `roster-dashboard` (`isMfaEligibleRole` excludes `crew`), but every role that can reach `/officers`, `/users`, `/applications`, `/upload-brief`, etc. is currently locked out of that app entirely. `apa` has no non-admin role, so it is 100% locked out.

**Desired behavior:**
Both apps implement a second login step: on `data.mfaStep === "challenge"`, show a TOTP code input and `POST` to `/manager/auth/mfa/challenge`; on `data.mfaStep === "enroll"`, drive the enrollment flow (QR/secret display, confirm code) before completing login. Only after that succeeds does the app treat the session as authenticated.

**Key interfaces:**
- `POST /manager/auth/login`, `POST /manager/auth/mfa/challenge`, `POST /manager/auth/mfa/verify-setup` — `artifacts/api-server/src/routes/auth.ts`
- Reference implementation to mirror: the 🛡️ MFA modal already built server-side in `artifacts/api-server/src/routes/manager.ts`

**Acceptance criteria:**
- [ ] `artifacts/apa`: a correct-credential login for an MFA-enrolled admin prompts for a TOTP code and succeeds with a valid code
- [ ] `artifacts/apa`: a correct-credential login for a not-yet-enrolled admin drives the enrollment flow and succeeds afterward
- [ ] `artifacts/roster-dashboard`: same two flows work for admin/manager/ic accounts
- [ ] Neither app shows a misleading "wrong role" error for what is actually a pending-MFA state

**Out of scope:**
- `artifacts/apa`'s separate bug where a 403 "pending approval" response is also mis-displayed as a role mismatch (same root symptom, different cause — noted here in case the same fix touches both, but not a blocker)
