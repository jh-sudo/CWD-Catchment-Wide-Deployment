## Agent Brief

**Category:** bug (security — brute-forceable auth bypass)
**Summary:** The `X-Manager-Pin` header bypass built into `requireManager` has no rate limiting anywhere except the one dedicated PIN-check endpoint, so the manager PIN can be brute-forced through any manager-gated route.

**Current behavior:**
`artifacts/api-server/src/routes/auth.ts:164-167`:
```ts
const pinHeader = req.headers["x-manager-pin"] as string | undefined;
if (pinHeader && pinHeader === appConfig.managerPin) { next(); return; }
```
This check runs before the session check on every `requireManager`-gated
route (dozens of endpoints across `leaveRequests.ts`, `phRoster.ts`,
`rosterPlan.ts`, `crms.ts`, `push.ts`, and — once `01-...` is fixed —
`deployments.ts`/`wls.ts`/`inspections.ts` too). Only the explicit
`/api/manager-pin/check` endpoint is wrapped in `makeAuthRateLimit()`
(`auth.ts:610`). The bypass baked into the middleware itself is unthrottled:
an attacker can guess the (short, numeric, default `"123456"`) PIN with
unlimited attempts by hammering any `requireManager` route with different
`X-Manager-Pin` header values, then gets manager-level access everywhere that
header is honored.

**Desired behavior:**
Guessing the manager PIN through the header bypass is rate-limited the same
way the dedicated check endpoint already is.

**Key interfaces:**
- `requireManager` — `artifacts/api-server/src/routes/auth.ts:164-167`
- `makeAuthRateLimit()` — same file, used at `auth.ts:610`

**Acceptance criteria:**
- [ ] Repeated wrong `X-Manager-Pin` values against any `requireManager` route get rate-limited (per-IP or per-IP+PIN-attempt counter), not just against `/api/manager-pin/check`
- [ ] A correct PIN still passes through immediately (no added friction for legitimate use)

**Out of scope:**
- Whether the header-bypass mechanism itself should exist at all (product decision, not addressed here)

## Comments

> *This was generated by AI during triage.*

Added a dedicated `managerPinBypassRateLimit` limiter (tighter than
`makeAuthRateLimit()`'s 10/15min — 3 attempts/15min, since this bypass has
no username/officerId to pair with the PIN) that `requireManager` runs
whenever a request carries `X-Manager-Pin`, before comparing it to
`appConfig.managerPin`. Split `requireManager` into itself (handles the
header path) plus a new `requireManagerSession` helper (the original
session-check body, unchanged) so a wrong/missing header still falls
through to the session check exactly as before.

Used `skipSuccessfulRequests: true`, unlike the endpoint-specific limiters —
essential here because a legitimate mobile caller sends this header on
*every* manager-gated request, not just once to "log in"; without it,
normal correct-PIN traffic would exhaust the budget and lock the caller out.
Only requests that end up failing (wrong PIN and no valid session cookie
either) count toward the limit.

Verified: `pnpm --filter api-server typecheck` and `build` clean. Ran the
server locally and confirmed with curl: repeated wrong `X-Manager-Pin`
values against `POST /api/deployments/reset` return 401 individually, then
429 once the 3-attempt budget is used up (matching `/api/manager-pin/check`'s
existing behavior — a correct guess after the budget is exhausted also gets
429 for the rest of the window, same as the dedicated endpoint); a correct
PIN sent before the budget is exhausted passes through immediately with no
added friction.

Threshold tightened from an initial 10/15min (matching `makeAuthRateLimit()`)
to 3/15min at the user's request.
