## Agent Brief

**Category:** bug (data integrity)
**Summary:** Three schema-level gaps: a missing foreign key, a child table with no primary key/unique constraint (allows silent duplicate rows), and no constraint tying `mfa_enabled` to `mfa_secret`.

**Current behavior:**
1. **Missing FK** — `lib/db/src/schema/leaveRequests.ts:38-41`: `icAccountId`
   has no `.references()` to `managersTable.id`. The inline comment justifies
   this as deferred because the managers table "lives in a separate
   domain/execution pass" — but `git log` shows `leaveRequests.ts` and
   `managers.ts` were added in the *same* commit (`d7fda06`), so that
   condition never actually existed, and it's gone unaddressed through 3
   subsequent commits including the MFA work. `ic_account_id` can currently
   hold any string, including a typo'd or deleted manager id, with zero
   DB-level enforcement.
2. **No PK/unique constraint** — `lib/db/src/schema/rosterDayOverrides.ts:20-29`:
   `rosterDayOverrideApplicationsTable` (the `DayOverrideEvent.applied[]`
   child table) has no `primaryKey()`/`unique()`, unlike every comparable
   child/junction table elsewhere in the schema
   (`deploymentAlertAcknowledgmentsTable`, `rosterOverridesTable`,
   `phRosterOverridesTable`, `deploymentEntriesTable`,
   `rosterCycleDutiesTable` all have one). A retried request or UI
   double-submit can silently duplicate a `(dayOverrideId, officerId, duty)`
   row, corrupting any count/audit view built on this table, and there's no
   conflict target to write a safe `onConflictDoUpdate` against.
3. **No MFA consistency check** — `lib/db/src/schema/managers.ts:30-31`:
   `mfaSecret` (nullable) and `mfaEnabled` (`notNull().default(false)`) have
   no constraint linking them, unlike the pattern this same codebase already
   uses for other paired nullable fields (e.g. `leave_requests_cover_status_check`
   uses an `IS NULL OR IN (...)` guard). A row with `mfa_enabled = true` and
   `mfa_secret = NULL` is representable — if any code path sets one without
   the other, that admin/manager/ic account would require an MFA code that
   can never be verified, i.e. a self-inflicted lockout on exactly the
   accounts `ac-2` MFA is meant to protect.

**Desired behavior:**
1. `leaveRequests.icAccountId` references `managersTable.id`.
2. `rosterDayOverrideApplicationsTable` has a primary key (or unique
   constraint) on `(dayOverrideId, officerId[, duty])` — confirm with a human
   whether multiple duties per officer per override is intentionally allowed
   before picking the exact column set.
3. `managers` has a CHECK constraint enforcing `mfa_enabled = false OR
   mfa_secret IS NOT NULL`.
