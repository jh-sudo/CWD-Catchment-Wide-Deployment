## Agent Brief

**Category:** task (hardening, low priority)
**Summary:** A hardcoded Maps API key, a container running as root, and a rate-limit gap that's only exploitable by a distributed attacker.

**Current behavior:**
1. `artifacts/api-server/src/routes/manager.ts:6` — Google Maps JS API key
   hardcoded in source (`const MAPS_KEY = "AIzaSy..."`) rather than read from
   env. Not a secret leak per se — client-facing Maps JS keys are inherently
   public once shipped to the browser (embedded in a `<script src>` at line
   ~3641) — but hardcoding makes key rotation and per-environment keys harder
   than an env var would.
2. `artifacts/api-server/Dockerfile` — the runtime stage has no `USER`
   directive, so the container runs as root.
3. `artifacts/api-server/src/routes/auth.ts` (`makeAuthRateLimit`) — TOTP
   verify rate limiting is per-IP only, no per-account counter. A
   distributed attacker (many source IPs) could still brute-force a 6-digit
   TOTP code since each IP gets its own fresh attempt budget. Low priority
   given the 30s code validity window already narrows this.

**Desired behavior:**
1. `MAPS_KEY` read from an env var, one per environment.
2. Runtime stage adds a non-root `USER` before `CMD`.
3. A per-account (not just per-IP) attempt counter backstops TOTP verification.

**Key interfaces:**
- `artifacts/api-server/src/routes/manager.ts:6`
- `artifacts/api-server/Dockerfile`
- `artifacts/api-server/src/routes/auth.ts` — `makeAuthRateLimit`, TOTP verify route

**Acceptance criteria:**
- [ ] Maps key comes from an env var, not a source literal
- [ ] Dockerfile runtime stage runs as a non-root user
- [ ] TOTP verification is throttled per-account in addition to per-IP

**Out of scope:**
- Restricting the Maps key by HTTP referrer in Google Cloud Console (an infra/console setting, not a code change)

**Fixed, all three items.**

1. `MAPS_KEY` now reads `process.env.GOOGLE_MAPS_API_KEY`, no hardcoded
   fallback — but doesn't hard-fail if unset (unlike `SESSION_SECRET`/
   `MFA_ENCRYPTION_KEY`), since a missing Maps key degrading just that one
   map (script tag won't load) is preferable to the whole dashboard being
   unbootable in an environment nobody's configured it for yet; logs a
   one-time warning instead. Documented in the README env-var table.
2. `Dockerfile` runtime stage now runs as `node` (the low-privilege user
   `node:20-slim` already ships, uid/gid 1000) via `COPY --from=builder
   --chown=node:node /app /app` + `USER node`. **Tried a separate `RUN chown
   -R node:node /app` first — measured 246s** (recursive chown over the
   whole `node_modules` tree) **vs 42.6s for `COPY --chown`**, so used the
   latter.
3. Added `makeAccountRateLimit()` — same shape as the existing per-IP
   `makeAuthRateLimit()`/`managerPinBypassRateLimit`, but keyed on the
   account being verified against (`pendingMfaManagerId` for `/mfa/
   challenge`, `resolveMfaEnrollmentSubject(req)?.id` for `/mfa/
   verify-setup`) instead of `req.ip`, so the 10-attempt/15min budget is
   shared no matter how many source IPs an attacker spreads across.
   `skipSuccessfulRequests: true`, same reasoning as the PIN-bypass limiter —
   a correct code is the expected case and shouldn't burn the budget.
   Applied to both TOTP-verify routes reachable off a pending (not-yet-fully-
   authenticated) session; left `/mfa/disable` alone since it's
   `requireManager`-gated (attacker already needs a hijacked authenticated
   session to reach it, a materially different threat model than the two
   pending-session routes).
