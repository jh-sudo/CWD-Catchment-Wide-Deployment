**Why `ready-for-human`:** fixing this meant either restoring the dropped

schema/contract decision, not a mechanical fix. The maintainer chose to

flagged during triage.

## Agent Brief

**Category:** bug
**Summary:** PH-imported roster swaps are indistinguishable from regular swaps in the UI

**Current behavior:**
`roster_swaps` has no column identifying a swap as PH-import-generated.
`ApplicationsManage.tsx` checks `phName`/`type`/`kind`, all undefined for
every PH swap, so they render with the wrong badge/label.

**Desired behavior:**
PH-imported swaps carry a `type` marker (`"PH"`) and a `phName` value that
the existing frontend detection logic picks up, restoring the pre-migration
"PH Swap" badge distinction.

**Key interfaces:**
- `roster_swaps` schema — needs `type` and `phName` columns (nullable —
  regular officer-initiated swaps don't set them).
- The PH-swap-import insert path — needs to populate both new columns.
- Any other `roster_swaps` insert site (e.g. regular officer swap creation)
  — needs to explicitly set `type: null, phName: null` since the insert
  type now requires them.

**Acceptance criteria:**
- [ ] `roster_swaps` has `type` and `phName` columns
- [ ] PH-import-generated swaps set `type: "PH"` and `phName`
- [ ] Regular officer-initiated swaps leave both null
- [ ] `ApplicationsManage.tsx`'s `isPHSwap` check correctly identifies
      PH-imported swaps again

**Out of scope:**

  `ph_roster_ref` on date + names if ever needed)
