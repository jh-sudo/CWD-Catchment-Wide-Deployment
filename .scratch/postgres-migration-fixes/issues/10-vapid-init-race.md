## Agent Brief

**Category:** bug
**Summary:** VAPID key initialization can crash the process on concurrent boot, and a transient failure is an unhandled rejection

**Current behavior:**
Two server instances (or a fast restart racing itself) booting concurrently
can both find no existing VAPID key row and both attempt to insert the
`id=1` row. The loser gets a unique-constraint violation on an unawaited,
unhandled top-level promise — an unhandled promise rejection that can crash
the process before any request arrives. Separately, `await vapidReady` call
sites use a non-null assertion (`vapid!.publicKey`) that would throw if
initialization ever failed for any other reason.

**Desired behavior:**
Concurrent boots never crash the process: the loser of the race reads back
the winner's keys instead of erroring. Any initialization failure (for any
reason) is caught, logged, and leaves the app in a degraded-but-running
state (push notifications unavailable) rather than crashing.

**Key interfaces:**
- The VAPID initialization function — insert should be conflict-safe
  (upsert-style: on conflict, re-read rather than error).
- The top-level initialization promise — needs a `.catch()` attached at
  creation so a failure can never surface as an unhandled rejection.
- Any consumer using a non-null assertion on the initialized value should
  handle the "never initialized" case explicitly (e.g. 503) instead of
  crashing on that specific request.

**Acceptance criteria:**
- [ ] Two concurrent boot attempts against an empty `vapid_keys` table both
      end up with the same keys, neither crashing nor throwing unhandled
- [ ] A failure during initialization is logged, not thrown as an unhandled
      rejection
- [ ] A request for the VAPID public key while initialization has failed
      returns a clean error response instead of a `TypeError` from a
      non-null assertion

**Out of scope:**
- Changing how VAPID keys are generated or rotated
