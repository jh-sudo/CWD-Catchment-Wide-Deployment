## Agent Brief

**Category:** bug
**Summary:** Concurrent leave-request submissions for the same officer+date can both succeed

**Current behavior:**
The duplicate check reads existing rows, then later inserts inside a
transaction. Two concurrent requests for the same officer and date can both
pass the read before either commits, producing two active (non-rejected/
cancelled) leave requests for the same officer+date.

**Desired behavior:**
It's impossible for two active leave requests to exist for the same
officer+date, enforced at the database level, not just the application
level. A conflicting request receives a 409, matching the existing app-level
check's behavior. Requests whose prior entry was rejected or cancelled must
still be allowed (this is a legitimate resubmission, not a duplicate).

**Key interfaces:**
- The leave-request table's schema — needs a constraint that only applies
  to "active" statuses (pending or approved), not rejected/cancelled ones.
- The insert path — needs to translate a constraint violation into the same
  409 response the app-level check already returns.

**Acceptance criteria:**
- [ ] A DB-level constraint prevents two active leave requests for the same
      officer+date
- [ ] The constraint does not block resubmission after a prior request was
      rejected or cancelled
- [ ] A conflicting concurrent insert returns 409 with a clear error message,
      not a generic 500

**Out of scope:**
- Changing the leave-request approval workflow itself
