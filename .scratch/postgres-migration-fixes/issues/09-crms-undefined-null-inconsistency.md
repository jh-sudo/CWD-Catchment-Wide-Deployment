Found during code review of the JSON→Postgres migration diff.
`POST /api/crms/ingest` builds its response by casting raw insert-value
objects to the select-row type instead of re-querying, so several nullable
fields never explicitly set on the insert are `undefined` rather than the
DB's actual `null` default.

## Agent Brief

**Category:** bug
**Summary:** CRMS ingest response omits keys that every other CRMS endpoint includes as null

**Current behavior:**
`JSON.stringify` drops `undefined` object keys, so the ingest response
silently omits fields like `assignedVehicleId`, `acknowledgedAt`,
`fpUpdatedAt`, etc., while `GET /crms/:id` for the same case immediately
after returns them as explicit `null`. A frontend doing key-presence checks
behaves inconsistently depending on which endpoint returned the case.

**Desired behavior:**
The ingest response has the exact same shape as every other CRMS endpoint —
unset nullable fields always appear as explicit `null`, never as a missing
key.

**Key interfaces:**
- The row-to-API-shape mapping function — should normalize nullable fields
  to `null` regardless of whether the input came from a real DB row or a
  freshly-built insert payload.

**Acceptance criteria:**
- [ ] The ingest response includes every nullable field explicitly, as
      `null` when unset
- [ ] `GET /crms/:id` immediately after an ingest returns byte-identical
      field presence (though possibly different `null` vs populated values
      as expected) to the ingest response

**Out of scope:**
- Re-querying the DB after insert (an alternative fix approach — not taken;
  normalizing the mapper is simpler and avoids an extra round-trip)
