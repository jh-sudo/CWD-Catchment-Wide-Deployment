history throws a Postgres foreign-key violation. Express auto-forwards the
rejection, producing a generic 500 with no indication of why — a regression
from the prior JSON-backed version, where delete always succeeded
unconditionally.

Mechanical fix applied directly in this session: `rosterPlan.ts`'s officer
DELETE handler now catches Postgres FK-violation (`23503`) and returns a 409
with an explanatory message, instead of letting it bubble to a generic 500.
The maintainer chose "block deletion with a clear error, no cascade" as the
default when this was flagged during triage — that's what's implemented.
Verified via `pnpm typecheck` (api-server package: clean).

Verified committed and present in code as of `d7fda06` (`rosterPlan.ts:557`).
That mechanical 409 fix has since been superseded, resolving the open decision
above: the maintainer chose **soft-delete** over blocking-only, cascade, or
hard-delete-with-reassignment. `DELETE /roster-plan/officers/:id` now sets
`officers.active = false` instead of attempting any DELETE — see the schema
comment in `lib/db/src/schema/officers.ts` and the "Officer deletion is
soft-delete" section in `CONTEXT.md` for the full rationale and every touched
call site (roster/PH generation filters, admin UI reactivate flow).

Rationale for soft-delete over the alternatives: block-only was safe but a
practical dead end (officers accumulate history within days, so nearly every
real officer becomes permanently undeletable); cascade risks silently
destroying leave/duty audit trail in a compliance-adjacent system, and PH
rotation's Rule A/B fairness lookback depends on that history surviving.
Soft-delete has neither downside and is reversible via the same PUT endpoint.

Known limitation, accepted as out of scope: there is no hard-delete path left
for a genuine zero-history duplicate/typo officer entry — it just becomes
permanently inactive. Not worth a separate admin affordance unless it becomes
a real nuisance in practice.
